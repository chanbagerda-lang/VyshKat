# ВышКат

Консольное приложение для учёта транспорта и инвентаря кикшерингового парка.

## Описание проекта

Программа позволяет добавлять транспорт и инвентарь, проводить техосмотр транспорта перед его регистрацией и получать информацию о состоянии парка.

В приложении реализованы:
- добавление самокатов, электросамокатов и велосипедов;
- учёт шлемов и зарядных станций;
- проверка исправности транспорта перед добавлением;
- подсчёт количества зарегистрированного транспорта;
- расчёт суммарного суточного энергопотребления;
- получение списка транспорта, подходящего новичкам;
- вывод названий и инвентарных номеров всех объектов.

Взаимодействие с программой происходит через консольное меню.

## Запуск программы

Из корневой папки проекта выполнить:

```bash
dotnet run --project VyshKat
```

После запуска появится меню, в котором можно выбрать действие. Для завершения работы используется команда `0`.

## Структура проекта

Основной проект находится в папке `VyshKat`, тесты — в `VyshKat.Tests`.

**Models** — классы транспорта и предметов:
- `Transport` — общий абстрактный класс транспорта;
- `Scooter`, `Bike`, `ElectricScooter` — конкретные виды транспорта;
- `Helmet`, `ChargingStation` — дополнительные предметы инвентаря.

**Interfaces** — интерфейсы:
- `IInventory` — объект с названием и инвентарным номером;
- `IEnergyConsumer` — объект, который потребляет электроэнергию;
- `IServiceCenter` — интерфейс проверки технического состояния транспорта.

**Services** — основная логика приложения:
- `ServiceCenter` — проводит техосмотр транспорта;
- `Fleet` — хранит зарегистрированные объекты, добавляет их и формирует отчёты.

**Program.cs** — консольное меню и настройка зависимостей.

## Архитектурные решения

Для разных видов транспорта используется наследование от абстрактного класса `Transport`. Это позволяет хранить их в одной коллекции и применять к ним общие операции.

Интерфейс `IInventory` объединяет транспорт и остальные предметы, так как у всех есть название и инвентарный номер.

Интерфейс `IEnergyConsumer` выделен отдельно, поскольку не каждый объект потребляет электроэнергию. Благодаря этому программа учитывает энергопотребление электросамокатов и зарядных станций без проверки конкретного типа каждого объекта.

За управление парком отвечает класс `Fleet`. Он проверяет уникальность инвентарных номеров, добавляет транспорт только после техосмотра и предоставляет методы для получения необходимой информации.

## Принципы SOLID

**Single Responsibility Principle**
Классы разделены по ответственности. `ServiceCenter` проверяет исправность транспорта, `Fleet` управляет парком, а `Program.cs` отвечает за взаимодействие с пользователем.

**Open/Closed Principle**

Использование базового класса `Transport` и интерфейсов позволяет добавлять новые виды транспорта, не изменяя основные методы подсчёта и получения списков в `Fleet`.

**Liskov Substitution Principle**
`Scooter`, `Bike` и `ElectricScooter` можно использовать там, где ожидается `Transport`. Для всех этих объектов доступны общие свойства и метод определения пригодности для новичков.

**Interface Segregation Principle**

Интерфейсы `IInventory` и `IEnergyConsumer` разделены. Например, `Helmet` реализует только `IInventory`, поэтому ему не требуется свойство энергопотребления.
**Dependency Inversion Principle**

`Fleet` зависит от интерфейса `IServiceCenter`, а не от конкретного класса `ServiceCenter`. Это позволяет заменить реализацию техосмотра без изменения `Fleet`.
## Dependency Injection

Для внедрения зависимостей используется `Microsoft.Extensions.DependencyInjection`.
В `Program.cs` регистрируются `IServiceCenter` и `Fleet`. DI-контейнер создаёт объект `Fleet` и передаёт ему необходимую реализацию интерфейса `IServiceCenter`.
Такой подход позволяет отдельно тестировать логику парка и заменять настоящий сервис техосмотра тестовой реализацией.

## Юнит-тестирование

Для автоматических проверок используется xUnit. Для подмены `IServiceCenter` применяется NSubstitute
Тесты проверяют:
- корректность создания транспорта и инвентаря;
- допустимые значения удобства использования;
- определение транспорта для новичков;
- проверку энергопотребления;
- успешную и неуспешную приёмку транспорта;
- подсчёт транспорта и суммарного энергопотребления;
- получение списка инвентаря;
- обработку повторяющихся инвентарных номеров;
- работу `Fleet` с подменённым сервисом техосмотра.

Запуск тестов:
```bash
dotnet test VyshKat.Tests
```
По результатам измерения покрытия:
- `Fleet` — 92,8%;
- классы моделей и `ServiceCenter` — 100%;
- общее покрытие приложения, включая `Program.cs`, — 47,6%.
Низкий общий показатель связан с тем, что интерактивное консольное меню не покрыто юнит-тестами. Основная логика приложения проверена отдельно.

## Ответы на обязательные вопросы
### 1. Какой принцип SOLID применён наиболее явно?

Наиболее явно реализован принцип Dependency Inversion Principle (DIP).
Класс `Fleet` зависит от интерфейса `IServiceCenter`, а не от конкретного класса `ServiceCenter`. Реализация техосмотра передаётся через конструктор. Благодаря этому можно изменить способ проверки транспорта, не изменяя код `Fleet`.

### 2. Какой принцип сознательно ограничен и почему?

Частично ограничен принцип Single Responsibility Principle (SRP).
Класс `Fleet` отвечает не только за хранение транспорта и вещей, но и за проверку уникальности инвентарных номеров, подсчёт энергопотребления и формирование списков.
Эти операции относятся к управлению одним парком, поэтому для небольшого учебного проекта я решила не выделять отдельные сервисы для каждой функции. Это позволило избежать лишнего усложнения архитектуры.

### 3. Что произойдёт при расширении программы?

При добавлении нового вида транспорта можно создать класс, наследующийся от `Transport`. Методы `Fleet` для подсчёта транспорта, получения инвентаря и определения пригодности для новичков продолжат работать без изменений.
Если новый транспорт потребляет электроэнергию, он должен реализовать `IEnergyConsumer`.
При этом потребуется дополнить консольное меню в `Program.cs`, чтобы пользователь мог создавать новый вид транспорта.
Если появится учёт сотрудников, понадобится отдельная модель, поскольку сотрудники не являются инвентарём парка. Для учёта склада запчастей также потребуется расширить модель и добавить соответствующую логику.


### 4. Какие тесты проверяют техосмотр и правило для новичков?

В `FleetTests.cs` методы `AddTransport_WorkingScooter_IncreasesCount` и `AddTransport_BrokenScooter_DoesNotIncreaseCount` проверяют принятие и отклонение транспорта.
В `TransportTests.cs` проверяется правило `EaseOfUse >= 6`. Дополнительно метод `GetBeginnerTransport_MixedEase_ReturnsOnlySuitable` проверяет формирование списка подходящего транспорта.
В `FleetMockTests.cs` используется библиотека NSubstitute. Она позволяет подменить `IServiceCenter` и заранее задать результат метода `Inspect()`.
В тестах подменённый сервис передаётся в `Fleet` через DI-контейнер. Это позволяет проверить, что решение о приёмке зависит от сервиса техосмотра.

## Вывод

В результате разработано консольное приложение для учёта транспорта и инвентаря парка. Реализованы основные функции управления парком, техосмотр, расчёт энергопотребления и получение списков объектов.

Разделение ответственности между классами и использование интерфейсов позволили сделать программу понятной и пригодной для дальнейшего расширения.
